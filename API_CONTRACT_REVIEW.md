# AstroOrbitX API Contract Review

> **SUPERSEDED (2026-11-15):** this review describes the former synthetic-only contract baseline. The [current API contract](./API_CONTRACT.md) is authoritative; retain this file only as historical review evidence.

**Review date:** 2026-11-14  
**Scope:** [`API_CONTRACT.md`](./API_CONTRACT.md) compared with current React types/adapters/pages, backend contract proposals, research notes, and available design assets. This is a documentation review only; no application code was changed.

## Summary

The contract correctly preserves the six required domain names, the four status values, independent status/coverage semantics, UTC-day inclusive trend ranges (maximum 31 days), null gaps instead of zero/interpolation, and explicit blockers for absent routes and scientific rules.

The largest risks are:

1. The contract still contains unresolved technical conventions that could be mistaken for approved API behavior (path prefix, serialization/envelopes, auth transport/session, and error mapping). These have been changed to **BLOCKED** where not supported by source.
2. The proposed intake retry key is the body field `client_record_id`; the contract had elevated an `Idempotency-Key` header and UUID server IDs without source approval. Header use and server ID format are now blocked.
3. Frontend metric/field names do not match several proposed canonical names: `temperature` vs `body_temperature`, `sleep` vs `sleep_duration`, `acquisition` vs `acquisition_type`, camelCase vs any wire naming, and `recordedAt` vs `measuredAt`.
4. Former product UI adapters/types were demo-only proposals and cannot be treated as contract confirmation. They have since been removed or retained only as presentation types; the current live adapter layer supports health/readiness only.
5. The approved Screens-2 PDF is absent from the workspace. The React screens can be inspected, but comparison to the approved visual source is not possible here.

## Contract changes made during review

Updated [`API_CONTRACT.md`](./API_CONTRACT.md) only to remove unsupported certainty and reconcile it with explicit source requirements:

- Marked base path, route style, snake_case, response/error envelopes, auth/session/CSRF, request ID, server ID format, pagination defaults, and server status-code mapping as blocked or proposals rather than adopted behavior.
- Kept UTC instants normalized to UTC and inclusive UTC calendar-date trends with a 31-day cap because the requirements support those semantics; kept history instant boundaries as a proposal because only the frontend proposal defines them.
- Recorded the proposed `client_record_id` body key and changed-payload conflict behavior; removed the implicit `Idempotency-Key` requirement and UUID server-ID assumption.
- Marked evidence ID type and baseline reference placement as blocked; removed an illustrative `baseline_version` property from the sample.
- Corrected field validation descriptions so UI “positive number” checks are not misrepresented as API/scientific bounds; highlighted the `temperature` / `body_temperature` mismatch.
- Kept canonical domains, assessment status values, status/coverage separation, no-zero/no-interpolation, privacy, baseline eligibility/version semantics, and radiation non-inference safeguards where directly supported.

No endpoint paths were added, and no scientific/product rule was approved by this review.

## Implementation-ready list

The following requirements can be implemented/tested without choosing an unresolved route or inventing a scientific rule. The API owner still must approve schemas and endpoint paths before exposing them over HTTP.

1. Use the six canonical domain identifiers exactly; maintain status values `normal`, `attention`, `urgent`, `insufficient_data` independently from coverage.
2. Preserve missing values as null/absent, never convert them to zero or `normal`; never interpolate missing days.
3. Implement/test trend date-range helper semantics already required: UTC calendar dates, inclusive `from` and `to`, max 31 requested days, one daily bucket per date, empty-day count 0 and null min/max/mean. Do not set per-metric count semantics for paired blood pressure until approved.
4. Ensure an assessment snapshot data model, once approved, retains the exact evidence references, ruleset version, evaluation time, and baseline identifier/version used. Do not invent the reference field placement/type.
5. Keep private note fields out of list DTOs, shared timeline, generic notifications, analytics and logs; perform filtering at the server boundary. Role policy for detail access remains blocked.
6. Preserve the required baseline eligibility rule: at least three valid pre-mission observations on three distinct UTC dates for HR/BP/body temperature; exclude suspect/stale/incompatible observations. Keep exact freshness/comparability/statistic behavior blocked.
7. Preserve measurement quantity separately from its unit; prohibit radiation inference/conversion/relabeling; do not use wearable, HR or solar illustrations as personal dosimetry.
8. Keep exercise records as one reusable activity/adherence context record, never a direct bone density/muscle mass/strength/fitness measurement.
9. Keep “acknowledged” distinct from “resolved”; a support request is not received by a responder absent explicit acknowledged state. Do not implement the proposed sync enum until approved.
10. Add contract-conformance tests for privacy and missing/null handling independently of route choices. Once a schema is approved, add exact status/coverage, idempotency, timestamps, role, units and response-shape tests.

## Blocked before API implementation

- One canonical route/method for each supported operation; profile selection and overview composition.
- Authentication provider/transport/session, role mapping, astronaut assignment, and private-detail permissions.
- Wire casing, metric/record field names, success/error envelopes, request correlation, ID format, status-code mapping, and idempotency key representation/scope/retention.
- Coverage enum/definitions and allowed status/coverage combinations.
- History category/filter schema, list field allowlist, page size/max/order, and whether structured psychological/symptom fields may be listed to any role.
- Timestamp property names/meaning, historical/future limits, UTC precision/offset acceptance, trend count scope, blood-pressure aggregation semantics, and excluded/suspect count schema.
- Exact baseline calculation/version lifecycle, freshness and comparability definitions; exact DEMO1 rule definitions; all psychological scales and radiation measurement semantics.
- Exercise plan/log schema; radiation interval boundaries/overlap/device-stream semantics; alert/support enums and transitions; timeline event schema and convergence window.
- OpenAPI publication and runtime validation behavior.

## Backend foundation follow-up (2026-11-14)

A subsequent implementation task approved a versioned `/api/v1` router, RFC 9457 errors with a request-ID extension, explicit development CORS origins, and a schema-only registry for the six canonical domain identifiers. The foundation now exposes only `GET /api/v1/health` and `GET /api/v1/ready`; these do not add product-data operations. The exact product routes, auth, domain-record schemas, and policies in the blocker list remain unresolved. The matching implementation and tests are recorded in the root audit and backend README.
